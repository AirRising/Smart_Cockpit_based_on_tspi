## 题目

### 03-01 谁保存状态，谁负责显示（5分）

输入：教程中的 `main`、`DemoVehicle`、`DashboardWindow` 三个角色，以及下面五项需求。

1. 保存当前整数车速；2. 收到定时器事件后计算下一车速；3. 把车速格式化成标签文本；
4. 创建服务并把服务交给窗口；5. 用户点击复位时发起请求。

约束：每项指定一个主要负责者，第 5 项还需标出请求终点；不能让服务持有窗口指针。
需提交：一张五行职责表，以及“复位请求”和“车速通知”两条方向不同的箭头。
验收/评分：五项各 1 分；把车速分别存在两个窗口、或让服务调用标签更新均不算正确分层。

### 03-02 晚到的窗口能否只靠信号（5分）

输入：服务已经到达 36 km/h 并暂停；此时新建窗口 B，只连接 `speedChanged`，标签初始文本为 `--`。
连接后没有再运行、复位或改变速度。窗口 A 已显示当前速度。

约束：不能为迎合 B 而让服务广播一次假的“变化”，也不能启动第二个定时器。
需提交：连接前、连接后、等待 1 秒后三个时刻的“服务 / A / B”表，及构造函数里的最小补充语句。
说明这条语句为什么不替代原有信号连接；可使用教程的 `showSpeed()` 和 `speed()`。
验收/评分：原行为预测 2 分，补充初始同步 2 分，区分查询与变化通知 1 分。

### 03-03 借用指针不等于拥有对象（5分）

输入：`main` 依次创建局部变量 `app`、`vehicle`、`window(&vehicle)`；窗口内部用 `new QLabel(this)` 创建标签。
服务中的 `QTimer m_timer` 是值成员，不是 `new` 出来的指针。

约束：按正常离开 `main` 的作用域推导，不考虑进程被强制结束；所有对象仍在主线程。
需提交：列出三个局部变量的销毁顺序，分别写清服务、定时器、标签由谁负责销毁。
再评审两条建议：“窗口析构时 delete vehicle”“moveToThread 后成员定时器自然就安全”。
验收/评分：销毁顺序 1 分，借用与值成员/子对象三种关系 2 分，两条建议的判断及原因各 1 分。

### 03-04 追踪定时步进、复位和通知次数（15分）

输入：未经修改的教程服务，初始车速 0、定时器停止；计数器在任何操作前连接，初始计数 0。
严格依次执行下表；“timeout”是已经实际交付的事件数量，不把墙上时间等同于事件数量。

| 步骤 | 输入操作 |
| --- | --- |
| A | `setRunning(true)` |
| B | 交付 119 次 timeout |
| C | 再交付 1 次 timeout |
| D | 再交付 1 次 timeout |
| E | `reset()` |
| F | 再交付 1 次 timeout |
| G | `reset()` |
| H | 再次 `reset()` |
| I | `setRunning(false)` |
| J | 暂停后等待 500ms，再 `reset()`；没有待处理的 timeout |

需提交：每步后的车速、运行/暂停状态、累计 `speedChanged` 次数，并标出哪些操作没有通知。
另外计算从启动到第一次回到 0 所需的理想模拟时长，以及车速 36 km/h 对应的 m/s。
约束：复位行为按教程原实现，不自行增加 stop；时长题只按每次 100ms 计算，不承诺真实计时精度。
验收/评分：车速序列 5 分，通知计数 5 分，运行状态 3 分，时长与单位换算各 1 分。

### 03-05 实现可晚加入的双视图（20分）

输入：自己的教程工程副本；保留一个 `DemoVehicle`，原窗口 A 是唯一提供运行/暂停与复位按钮的窗口。
新增只读窗口 B `SpeedMirror`，同时显示 km/h 和保留一位小数的 m/s。

约束：B 只订阅同一个服务并查询初值；不保存第二份可独立修改的车速，不创建模拟定时器。
服务不得 include UI 头文件；B 不提供独立运行按钮，避免把未同步的按钮选中状态当作服务状态。
B 的创建时机由你的入口或 A 中的“打开镜像”操作安排，不能只测试程序启动时的零值。
需提交：B 的头/源文件、组装入口和 CMake 改动，全部位于练习目录；另附四项观察记录。

- 服务到达非零值并暂停后才创建 B，观察 B 是否立即显示。
- 验证 36 km/h 的换算；可复用下一题的确定性步进，不能新增 UI 私有速度。
- 继续运行，比较 A 与 B 的 km/h；复位后比较两者。
- 暂停后重复复位，记录服务信号次数，而不只截取标签显示。

验收/评分：单一状态与单向依赖 5 分，B 初始同步 5 分，单位显示 4 分，双视图行为记录 4 分，构建纳入新文件 2 分。

### 03-06 给时间驱动增加确定性测试入口（20分）

输入：教程用定时器 lambda 推进车速，难以精确地在某个 timeout 停住。
在练习副本把“一步更新”提取为 `advanceOnce()`，定时器仍以 100ms 调用它；不修改参考仓库。

约束：保留唯一的 `setSpeed()` 比较/通知出口；`reset()` 不改变定时器状态。
`advanceOnce()` 是本题明确增加的教学测试接口，不声称参考教程本来就有它；测试调用它不表示定时器正在运行。
需要检查运行状态时，可新增只读 `isRunning()`，返回定时器是否活跃，不能另存一份可能失步的 bool。
需提交：服务改动及一个独立的 QtCore 检查入口，失败时打印用例名并返回非零退出码。

检查入口至少覆盖：初始状态、推进到 36、推进到 120 后再走一步、非零复位、零值连续复位。
另在同一线程中连续执行“启动、复位、读取运行状态、停止、复位、读取运行状态”；这段期间不进入事件循环。
用普通 `QObject::connect` 计数；无需 QtTest，也不要用等待 12 秒来代替确定性推进。
验收/评分：提取后仍为原步进规则 5 分，变化通知与复位语义 5 分，确定性断言和退出码 6 分，计时状态及构建记录 4 分。

### 03-07 三份构建故障单（15分）

输入：以下是三个相互独立的练习副本，不是同一个工程连续出现的错误。

| 副本 | 已知改动 | 现象 |
| --- | --- | --- |
| X | 保留 `Q_OBJECT`，关闭 AUTOMOC，使用全新构建目录 | 链接时报元对象或信号相关未定义符号 |
| Y | AUTOMOC 开启，目标中有头文件，但漏列 `DemoVehicle.cpp` | 构造函数、getter 等实现未定义 |
| Z | 文件移入 `core/`，目标已列新路径，UI 仍 include `"DemoVehicle.h"`，没有配置 core 头文件搜索目录 | 编译时报找不到头文件 |

需提交：每份的失败阶段、最小修复位置、修复后如何验证；并反驳“手写 speedChanged 函数体即可修好 X”。
约束：只提出并在自己的副本实施修复；不能通过链接参考仓库已有二进制掩盖漏编译问题。
Z 需说明源文件清单与 include 搜索目录为何不能相互代替；不要把所有 vtable 错误都归因于同一原因。
验收/评分：X 的 moc 机制与修复 6 分，Y 的实现入目标 5 分，Z 的搜索路径与验证 4 分。

### 03-08 设计一份可复核的分层验收（15分）

输入：合并第 05、06 题的练习成果，布局为 `core/`、`ui/`，同时提供 GUI 入口与无界面的检查入口。
要求两个可执行目标复用同一份服务实现；服务库只依赖 QtCore，UI 目标依赖 QtWidgets。

需提交：一张目标依赖图、关键 CMake 目标声明，以及下列脚本化操作的期望/实际结果表。

1. 不开启定时器，推进至 36，然后创建 A 与 B。
2. 再推进一次，只通过服务传播变化；随后复位两次。
3. 在服务仍存活的范围内销毁 B，再创建 B；继续推进一次。
4. 销毁窗口后再销毁服务；单独构建并运行无界面检查入口。

约束：解释 core 公共头文件依赖 QObject 时 QtCore 使用要求如何传给使用者；不能靠 UI 间互相读取标签同步。
未运行的项目填“未运行”，附计划命令和依赖缺口，不得用推导值冒充日志；不要求部署或全项目构建。
验收/评分：目标和依赖传播 5 分，操作结果与信号计数 6 分，生命周期安排及证据边界 4 分。

## 参考答案

<details><summary>参考答案与评分提示（先独立完成）</summary>

**03-01**
- 五项依次为服务、服务、窗口、main、窗口发起而服务执行。
- 请求路径：按钮 → `DemoVehicle::reset()`；通知路径：服务改变状态 → `speedChanged` → 窗口显示。显示文本不是第二个业务状态源。

**03-02**
- 三个时刻的原行为均为“服务 36 / A 显示 36 / B 显示 --”；等待本身不制造变化信号。
- 在连接后调用 `showSpeed(vehicle->speed());`。这是构造函数内的 C++ 片段，非完整文件。
- getter 补上订阅前的状态，信号负责订阅后的变化；不应为初始化显示而额外 emit。

**03-03**
- 局部变量依次销毁 window、vehicle、app；窗口借用 vehicle，不负责 delete 它。
- `m_timer` 随服务作为值成员销毁；标签作为窗口的 QObject 子对象自动销毁。不要重复手动删除。
- 任意 moveToThread 不能保证值成员定时器归属、访问及启动操作都正确；本题维持主线程设计。

**03-04**

| 步骤 | 车速 | 定时器 | 累计通知 |
| --- | --- | --- | --- |
| A | 0 | 运行 | 0 |
| B | 119 | 运行 | 119 |
| C | 120 | 运行 | 120 |
| D | 0 | 运行 | 121 |
| E | 0 | 运行 | 121 |
| F | 1 | 运行 | 122 |
| G | 0 | 运行 | 123 |
| H | 0 | 运行 | 123 |
| I | 0 | 暂停 | 123 |
| J | 0 | 暂停 | 123 |

- A、E、H、I、J 没有速度通知；首次回零为第 121 步，理想时长 12.1 秒。36 ÷ 3.6 = 10 m/s。

**03-05**
- 检查 B 构造时查询服务、后续只连同一服务；36 时显示 `36 km/h`、`10.0 m/s`，37 时第二项显示 `10.3 m/s`。
- 使用浮点除法 `speed / 3.6`，不能先做整数截断。A、B 的速度一致，运行中复位后下一步继续增长。
- 新窗口不应额外增加服务通知；从非零复位一次有一条通知，再次复位没有。只有截图而没有计数证据不能拿满行为分。

**03-06**
- 单步仍调用 `setSpeed((m_speed + 1) % 121)`；这是成员函数内的 C++ 检查点，非完整文件，不提供整个实现。
- 新服务从 0 推进 36 次：速度 36、通知 36；继续推进 84 次：120、120；再一步：0、121。
- 若随后再走一步并复位两次：速度依次 1、0、0，累计通知 122、123、123。
- 不处理事件的“启动→复位→查询”应仍运行；“停止→复位→查询”仍暂停。零值复位不新增通知，手动单步不改变运行开关。

**03-07**
- X 是链接阶段缺少元对象实现：恢复 AUTOMOC、确认带 `Q_OBJECT` 的头文件进入目标，重新配置并构建；信号实现由 moc 生成，不能手写替代。
- Y 是链接阶段缺少普通实现：把 `DemoVehicle.cpp` 加入对应目标，不只是 include 头文件或链接 Qt。
- Z 是预处理/编译阶段搜索路径缺失：为使用者配置 core include 目录，或使用正确相对 include。源文件列表决定编译什么，include 目录决定去哪里找头文件。

**03-08**
- 目标可为 `vehicle_core`、GUI、检查入口；后两者链接前者。core 公共头依赖 QObject，可将 `Qt5::Core` 和 core include 目录作为 PUBLIC 使用要求；GUI 的 Widgets 可设 PRIVATE。
- 若从服务创建时开始计数：36 次推进后为 36 条；创建 A/B 不增计数；再一步 37 条；两次复位后为 38 条；重建 B 不增加；最后一步为 39 条。
- 初建 A 显示 36 km/h，B 同时显示 36 km/h 和 10.0 m/s；下一步 B 为 37/10.3，复位后为 0/0.0；重建 B 立即显示 0/0.0，最后一步为 1/0.3。A 始终显示对应的 km/h。
- 服务生存期包住所有窗口和连接；无界面入口不应链接 UI 实现。可类比只读参考 [main.cpp](../../src/main.cpp) 的组装职责，不能声称本题已复现整个参考工程。
