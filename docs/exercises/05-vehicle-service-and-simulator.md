## 题目

### 05-01 两条数据路径能证明什么（5分）

输入：A 通过已存在的真实 socket 接收帧；B 在主线程运行 `SignalSimulator`，只调用 `setSimulatedMode(true)`，从未打开 socket。
本题仅画图，不实际建立 A 路径。

需提交：分别把 SocketCAN、CanManager、队列信号、CarService、SignalSimulator、UI 放入适用的路径。
回答 B 中“状态在动、canConnected 为 true、framesReceived 为 0”是否互相矛盾，以及这能否证明真实收帧正常。
约束：必须区分“调用服务入口”与“操作系统 socket 收帧”；不得把界面变化次数称为总线吞吐量。
验收/评分：真实路径 2 分，模拟路径 1 分，三个观测值的解释及证明边界 2 分。

### 05-02 QThread 对象和 run 在哪里执行（5分）

输入：CanManager 对象与 CarService 对象都在主线程创建；接收信号到服务的连接明确为 `Qt::QueuedConnection`。
主线程正在执行一段耗时 300ms 的同步工作，此时接收线程读到了一帧。

需提交：标出 CanManager 对象归属、`run()`、`onCanFrame()`、普通 `sendFrame()` 调用各自的线程规则。
再说明排队帧和模拟器定时器在这 300ms 内会怎样；不要推断一定积累恰好三次 timeout。
约束：这是静态追踪，不实际阻塞应用；现有发送 mutex 不能被当作整个对象线程安全的证明。
验收/评分：对象与 run 区别 2 分，槽和普通方法规则 2 分，事件循环阻塞影响 1 分。

### 05-03 挡位位置和倒车标志不是同一件事（5分）

输入：`0x300` 的 byte0 为 `01`，其余字节为 0；使用教程现有 `handleFrame300()`，初始挡位 P、倒车 false。
同学把 DBC 的 `gear_signal` 起始位改到 byte1，期望同一帧产生不同挡位。

需提交：根据 bit0 与 bits1..3 分别说明这帧携带的两项状态；评审“bit0 为 1 就一定是 R”的说法。
再预测仅修改 DBC 对当前挡位处理的影响，并说明为什么没有达到同学的目标。
约束：按现有实现回答，不设计自动纠正矛盾组合的策略；本题也不允许实际修改项目 DBC。
验收/评分：两个状态 2 分，区分位置与倒车标志 1 分，绕过 DBC 的事实和影响 2 分。

### 05-04 逐帧追踪有效状态与变化通知（15分）

输入：全新的服务，初始 speed=0、gear=P、reverse=false、angle=0；四种变化信号计数均为 0。
在主线程按表顺序直接调用 `onCanFrame()`，不启用模拟器或 socket，也不更改 DBC。

| 步骤 | ID | payload（十六进制） |
| --- | --- | --- |
| A | 0x100 | `78 00 B8 0B 64 01 00 00` |
| B | 0x100 | 与 A 完全相同 |
| C | 0x100 | `FF FF B8 0B 64 01 00 00` |
| D | 0x100 | `78 00 B8 0B 64 01`（只有 6 字节） |
| E | 0x300 | `01` |
| F | 0x300 | `03` |
| G | 0x300 | `04` |
| H | 0x300 | `06` |
| I | 0x400 | `9C FF` |
| J | 0x400 | `9C` |

需提交：每步后的 speed、gear、reverse、angle，以及四种信号的累计次数；不要求不同信号之间的发射先后顺序。
C 需单独写出原始车速和业务车速；D/J 需指出拒绝发生在哪一层，而不是写“没有数据所以归零”。
约束：挡位允许一字节输入；整数、布尔按值比较，double 沿用服务的近似比较，不把接收次数当变化次数。
验收/评分：车速与 clamp 5 分，挡位/倒车状态及计数 6 分，方向盘 2 分，重复/短帧不通知的解释 2 分。

### 05-05 实现无需 CAN 的服务回归入口（20分）

输入：只读复用 [CarService](../../src/core/CarService.h) 及教程列出的实现文件。
在学习目录写 `service_regression.cpp` 与自己的 CMake，使用 QtCore，连接 lambda 统计速度通知。
不要调用 `car.start()`；所有直接注入都在创建服务的主线程中执行。

第一组使用内置表，按顺序注入 0x100：好帧 `7800B80B64010000`、空帧、好帧前 6 字节、`FFFFFFFFFFFFFFFF`、重复全 FF 帧、好帧前 7 字节。
逐次检查 speed/rpm/fuel 和速度通知累计数，必须报告失败用例名，不能只打印最终车速。
第二组另建服务，先注入好帧，再仅覆盖一条 speed（Intel `0|16`，factor=1、offset=0）的 DBC。
对 `C800000000000000` 分别检查解析器能否得到 speed，以及服务是否接受这份不完整字段集合。

需提交：独立检查入口、构建文件、两组逐步检查结果；返回非零代表失败，不需要 QtTest。
约束：检查 decode 的 bool 和字段集合，不以 `QHash::value()` 的缺省零假装字段存在。
可调整教程 CMake 的入口文件名并保留 AUTOMOC；其源码只读路径和所有构建输出必须分开。
验收/评分：正常/短帧/7 字节边界 6 分，三项 clamp 与 change-only 5 分，部分 DBC 不损坏旧状态 6 分，独立构建与诊断 3 分。

### 05-06 实现不用等一分钟的模拟时序模型（20分）

输入：教程模拟器每次 tick 先累计 100ms，每圈 60000ms；每次计划注入 0x100、0x300、0x400。
在练习目录写独立 `timeline_lab.cpp`：实现 `stateAt(elapsedMs)` 和一个从第 1 次到第 600 次 tick 的循环。
`stateAt` 返回圈内时间、阶段、倒车标志；这是学习用逻辑模型，不修改或冒充生产模拟器的真实输出。

阶段按教程分为加速、巡航、减速、停车、倒车；使用半开区间表达边界，52 秒后仍属停车段。
需提交：模型入口、600 行 CSV 或等价表格、每种帧的计划数量、倒车 tick 数与倒车标志变化次数。
另单列累计时间 0、100、44900、45000、51900、52000、59900、60000、60100ms 的结果。
在 44900、45000、51900、52000ms 四点补写预期挡位 byte0；这里只涉及停车与倒车，不需要复刻速度波形。

约束：不使用真实等待来推进逻辑时间，不访问 SignalSimulator 私有成员，不通过修改源码加快计时器。
明确 start 清零时是否已经产生一个 tick，不能把第 600 次 tick 误当作下一次才回卷。
输出数量只能叫“模型计划注入数”，不是 socket 接收量或实测带宽；模型不产生空调 ACK。
验收/评分：逻辑时钟/回卷 5 分，倒车边界与挡位字节 6 分，三帧统计 5 分，可重复入口和证据边界 4 分。

### 05-07 三张故障截图背后的不同原因（15分）

输入：以下是三份独立故障描述，均不要求实际建立总线。

- X：纯模拟下仪表在动，`framesReceived()` 一直是 0；同学建议重装驱动，并增加 0x200 ACK 计数作为模拟器健康条件。
- Y：修改 DBC 的挡位布局后，挡位仍按旧 byte0 变化；同学认为“DBC 加载失败”是唯一可能。
- Z：离线审阅发现 `sendFrame()` 对扩展 ID 也先与 `CAN_SFF_MASK` 相与，再添加 `CAN_EFF_FLAG`。

对 Z，给定 ID=`0x12345`、extended=true、SFF_MASK=`0x7FF`、EFF_FLAG=`0x80000000`。
需提交：X/Y 各一条可证伪的诊断步骤；Z 的有效 ID 位和含标志的计算结果，并与目标值比较。
最后写一个只针对 Z 的未来离线回归用例条件，不实现修复、不发送帧。
约束：区分正常设计边界与现有缺陷；不能将扩展帧发送写成“已支持”或“已修复”。
验收/评分：X 的两类计数/ACK 边界 5 分，Y 的实际数据入口 5 分，Z 的位计算及回归条件 5 分。

### 05-08 设计有证据边界的离线验收（15分）

输入：你已具备第 05 题检查入口和第 06 题时序模型，现在要交付一份有限时长、可复核的服务验收计划。
使用三个相互独立的新服务实例；不调用 start、不打开任何接口，所有观察对象在退出前仍存活。

1. 实例 A：先注入未知 ID `0x555` 的 8 字节零，再注入好帧两次，区分连接状态、有效车速和速度通知。
2. 实例 B：设置模拟模式，创建真实 SignalSimulator，调用 start；事件循环约 1200ms 后 stop 并退出。
3. 实例 C：不启动模拟器，依次直接注入 `0x300:01`、`0x300:03`、`0x300:00`，作为边界验证。

需提交：每项的操作顺序、观察 getter/信号、期望值或合理范围、失败定位，以及“本项没有证明什么”。
给出 B 的定时退出/对象销毁安排和额外的外部超时兜底方案，避免无限等待；可提交步骤而非完整程序。
还需说明：如何用第 06 题验证整圈逻辑，却不谎称短时间实测已经覆盖 45 秒倒车边界或空调确认。
约束：B 不要求精确速度、精确 tick 数或固定墙钟吞吐；若没有 Qt 环境，只交计划并明确“未运行”。
验收/评分：三组可核对期望 6 分，分层故障定位 4 分，有限退出及证据限制 5 分。

## 参考答案

<details><summary>参考答案与评分提示（先独立完成）</summary>

**05-01**
- 真实：SocketCAN → CanManager 接收线程 → queued 信号 → 主线程 CarService → UI；模拟：主线程 SignalSimulator → `onCanFrame()` → 状态/信号 → UI。
- 纯模拟绕过 socket；模拟模式使健康判断的 canConnected 为 true，socket 计数可以一直为 0。三者不矛盾，但不能证明真实 CAN 接收或带宽。

**05-02**
- CanManager 这个 QObject 归主线程，只有重写的 run 在接收线程执行；queued 槽在 CarService 所属主线程执行。
- 普通 sendFrame 在调用它的线程执行，不会自动进入 run 的线程。主线程阻塞时槽和定时器等待事件循环，不能按 300/100 推断必有三次超时补发。

**05-03**
- `01` 的 bit0 为 1，位置位为 0，因此是 P + reverse=true，而非完整 R；`03` 才是 position=1 且 reverse=true。
- 当前 [CarService.cpp](../../src/core/CarService.cpp) 的挡位处理直接读 byte0，绕过 DBC；移动 DBC 信号起始位不会改变这段代码。

**05-04**

| 步骤 | speed / 累计次数 | gear / reverse | gear 次数 / reverse 次数 | angle / 累计次数 |
| --- | --- | --- | --- | --- |
| A | 120 / 1 | P / false | 0 / 0 | 0 / 0 |
| B | 120 / 1 | P / false | 0 / 0 | 0 / 0 |
| C | 240 / 2 | P / false | 0 / 0 | 0 / 0 |
| D | 240 / 2 | P / false | 0 / 0 | 0 / 0 |
| E | 240 / 2 | P / true | 0 / 1 | 0 / 0 |
| F | 240 / 2 | R / true | 1 / 1 | 0 / 0 |
| G | 240 / 2 | N / false | 2 / 2 | 0 / 0 |
| H | 240 / 2 | D / false | 3 / 2 | 0 / 0 |
| I | 240 / 2 | D / false | 3 / 2 | -10 / 1 |
| J | 240 / 2 | D / false | 3 / 2 | -10 / 1 |

- C 的 unsigned raw=65535，解析器得到该值后，服务 clamp 到 240；D/J 在整帧解码长度校验处失败，保留状态。B 是重复有效值，不发速度变化信号。

**05-05**
- 第一组 `(speed,rpm,fuel;速度累计通知)` 依次为 `(120,3000,50;1)`、同前、同前、`(240,8000,100;2)`、同前、`(120,3000,50;3)`。
- 7 字节已包含内置 0x100 的全部字段，6 字节不足；全 FF 的三个原始值分别为 65535、65535、127.5，服务做业务范围限制。
- 第二组解析器成功且只给 speed=200；服务缺少 engine_rpm 等必需字段，仍保留 120/3000/50，速度计数仍为首次好帧产生的 1。
- 检查失败要返回非零；CMake 保持 AUTOMOC 并列入教程所需实现，不能只包含头文件。未实测时不应打印“通过”作为提交证据。

**05-06**
- 圈内时间为 elapsedMs%60000；阶段区间为 `[0,8000)` 加速、`[8000,30000)` 巡航、`[30000,40000)` 减速、`[40000,45000)` 停车、`[45000,52000)` 倒车、`[52000,60000)` 停车。
- 指定时间对应：0→加速/false，100→加速/false，44900→停车/false，45000→倒车/true，51900→倒车/true，52000→停车/false，59900→停车/false，60000→圈内0/加速/false，60100→圈内100/加速/false。
- 四点挡位字节依次 `00、03、03、00`。倒车窗口方向盘模型为零，不要求生成转向轨迹。
- start 清零不算 tick；第 1 次到 100ms，第 600 次到累计 60000ms 并回卷。倒车是第 450..519 次，共 70 次，标志变化 2 次。
- 每个 tick 计划三帧，三个 ID 各 600 帧，共 1800 帧；0x200 和 ACK 均为 0。这是离线模型计算，不是对 [SignalSimulator.cpp](../../src/core/SignalSimulator.cpp) 的实测计数。

**05-07**
- X：检查是否仅走直接注入、是否根本未打开 socket；计数来源是 CanManager。模拟器不产生 0x200 或 ACK，不应以缺少 ACK 判定其速度模拟失败，也不应据此重装驱动。
- Y：检查 handleFrame300 的实际读取位置，即可证伪“只能是加载失败”；其 byte0 读取独立于 DBC 表。若练习目标是 DBC 驱动挡位，需要另行设计，当前未实现。
- Z：`0x12345 & 0x7FF = 0x345`；当前构造结果为 `0x80000345`，目标应保留 29 位 ID，为 `0x80012345`。补 EFF 标志无法恢复丢失的高位。
- 未来回归至少覆盖本例及标准 ID 掩码不退化，离线检查帧头构造即可；这是暴露现有发送掩码缺陷，不是修复完成或实车验证。

**05-08**
- A 在主线程连续注入、期间不等待连接超时：未知帧可刷新收帧连接状态但 speed 仍为 0、速度计数 0；首个好帧为 120/1，重复后仍为 120/1。三次直接注入都不增加 socket 计数。
- B 正常处理事件时，约 1.2 秒可观察到 speed>0、canConnected=true；未开 socket 时 framesReceived=0。必须分别记录实际值，不规定准确速度或通知次数。
- B 使用 QTimer::singleShot 安排 sim.stop、car.stop 和 app.quit；可给学习入口设置例如 5 秒外部 timeout，超时记为未完成/失败而非成功。退出与服务/模拟器生命周期要有序。
- C 的状态依次 P/true、R/true、P/false；gear 累计次数为 0、1、2，reverse 为 1、1、2。无需 CAN、UI 或相机即可检验这种组合。
- 状态不动先查事件循环/模拟器 start，再查解码/字段/重复值；连接为真不保证有效车速新鲜。第 06 题只证逻辑模型，B 只作短时联调，均不证明 socket、整圈真实时序、空调 ACK 或扩展帧发送正确。
