## 题目

### 07-01 三份状态分别由谁负责（5分）

- 输入约束：车辆初始为默认 ClimateState；用户把温度滑块调到 24，但尚未收到任何回传。
- 任务：分别说明已确认状态、控件编辑值、待确认目标的所属对象、更新时间和用途。
- 任务：补充本地待处理编号的作用，判断它是否应当作为第四份空调业务状态。
- 学生提交物：一张“数据／所有者／何时变化／失败后用途”表。
- 验收/评分点：三份状态区分 3 分，本地编号与业务状态区分 1 分，确认前不提前提交 1 分。
- 作答边界：区分“目标温度”“已确认设定温度”与“实际车厢温度”。

### 07-02 什么回传能完成请求（5分）

- 输入约束：pending 目标合法；回传分别为仅风量不同的 ACK、匹配 ACK、普通状态上报和缺第三字节的帧。
- 任务：查找匹配字段和解码前提，给出各输入是否改变已确认状态及依据。
- 任务：另外考虑服务空闲时收到两类完整回传，解释是否通知 UI。
- 学生提交物：按 pending/idle 分组的判定表，注明应用层与链路层应答的区别。
- 验收/评分点：完整字段和匹配条件 2 分，pending 分支 1 分，idle 分支 1 分，ACK 层次 1 分。
- 作答边界：匹配依据以解码后的状态为准，不假定所有 payload 位都必须相同。

### 07-03 两个计时器与一次受理（5分）

- 输入约束：连续拖动滑块，尚无 pending；发送接口随后返回非零编号，但 CAN 没有打开。
- 任务：查出两个单次定时器的间隔、起算点以及哪些事件会停止或重启它们。
- 任务：解释再次调用发送接口、编号为 0、编号非零分别表示什么。
- 学生提交物：两条时间轴，加一个“受理／传输／执行”证据层次表。
- 验收/评分点：防抖 2 分，ACK 等待 1 分，拒绝重入与编号语义 2 分。
- 作答边界：不要以日志中的一个 `sent` 单词替代对发送路径的检查。

### 07-04 手算报文并推演编辑到确认（15分）

- 输入约束：默认状态开始；t=0 温度变 23，t=100 温度变 24，t=180 风量变 5；模式 0、AC 开、自动关始终不变。
- 输入约束：t=500 注入仅风量为 4 的 ACK；t=550 注入温度 26 的 ack=false 上报；t=700 注入最终目标的正确 ACK。
- 任务：查教程字段位表，手算最终目标的 8 字节命令及 ACK，展示 byte1 的位组合过程。
- 任务：列出防抖重启、服务受理、ACK 截止、三份状态及结果信号的变化。
- 任务：再删除 t=700 的回传，推演等待结束后的状态；假定所有计时器按期交付。
- 学生提交物：十六进制表、事件时间线、成功/超时两个终态。
- 验收/评分点：命令与 ACK 5 分，两个计时起点 4 分，错误/普通回传处理 3 分，终态及信号 3 分。
- 作答边界：本题只是进程内推演，不提供真实 CAN 发送命令。

### 07-05 实践：建立服务闭环回归用例（20分）

- 输入约束：学习副本中每个场景新建服务或重置模型；不调用 `start()`，目标采用上一题五字段。
- 任务：编写 ack、timeout、cancel、stop 四个场景；受理后 50ms 注入单字段错误 ACK，100ms 执行场景动作。
- 任务：受理后立即再次发送，并尝试用 0、错误编号取消；900ms 检查信号次数、pending 和已确认状态。
- 任务：另加两字节回传，以及依次只改温度、风量、模式、AC、自动模式的五种错误 ACK。
- 学生提交物：可核对的测试源/脚本、输入夹具、断言表，列明同步注入与异步等待的区别。
- 无硬件替代：用纯脚本实现虚拟时钟和五字段状态机；无执行环境交测试源及四条完整纸面轨迹。
- 验收/评分点：四种结果与单一终结信号 8 分，完整五字段和缺字段测试 5 分，拒重入/取消编号 4 分，计时证据 3 分。
- 编码约束：同步注入后直接检查已发生的信号；只对未来定时事件等待，不以 sleep 阻塞事件循环。
- 作答边界：测试通过仅说明服务或模型的逻辑，不能声称实际发送成功。

### 07-06 实践：防抖、回填与旧通知隔离（20分）

- 输入约束：修改 ClimatePage 学习副本或建立不创建窗口的 UI 状态模型；使用可控时间和假服务编号。
- 任务：在 0、60、120、180ms 调节控件；记录发送次数和最终目标，再模拟服务回填时控件发变化通知。
- 任务：请求 r1 取消后创建 r2；分别向三个结果处理入口投递 0、r1、r2，验证处理边界。
- 任务：另设外部请求占用服务，使 UI 的发送返回 0；检查控件值、取消按钮、状态文案与本地编号。
- 学生提交物：测试源/事件模型、至少六组断言及 UI 状态转移表；不提交整套窗口实现。
- 无硬件替代：只模拟控件值、使能状态和编号；若无 Qt，提交脚本或逐条纸面事件轨迹。
- 验收/评分点：防抖合并 5 分，回填抑制新请求 4 分，旧/零编号隔离 5 分，拒绝发送与结果文案 6 分。
- 编码约束：每次测试当前编号结果时重新准备 r2，避免上一个结果清掉编号后污染下一场景。
- 作答边界：测试应忠实记录温度 +/- 的现状，不把“不能重复发送”误写为“所有控件完全锁定”。

### 07-07 排障：数字往返成功，功能仍有疑问（15分）

- 输入约束：收到四份报告：`--sim` 总超时；模式 1 的 UI 文字与协议说明不同；循环风切换无命令；等待时 +/- 还能改显示。
- 任务：逐项定位到服务、协议注释或 UI 接线，给出可证伪的检查项。
- 任务：区分“现有功能”“已知缺陷”“未来建议”，避免把回传字节一致当成功能语义正确。
- 学生提交物：四行排障表及处理优先级，引用函数/字段而不是仅引用教程结论。
- 验收/评分点：模拟器行为 3 分，模式注释冲突 4 分，循环风缺口 4 分，锁定缺口 4 分。
- 无硬件替代：源码检查与纸面按钮事件足够；制冷、风向、循环风硬件结果均标“未验证”。
- 作答边界：不修改 DBC、配置或参考仓库，也不为循环风私自分配线上位号。

### 07-08 综合：取消与同目标迟到 ACK（15分）

- 输入约束：初始已确认 22℃；t=0 直接受理目标 T=24℃/风量5/模式0/AC开/自动关，编号 r1；t=100 正确取消 r1。
- 输入约束：t=150 再受理相同 T，编号 r2；t=200 到达由 r1 引发的完整匹配 ACK；t=220 到达本地旧结果通知 r1。
- 任务：按当前实现推演服务和 UI 的行为，评估本地编号与线上回传分别能辨认什么。
- 任务：另起分支：取消后不创建 r2，先到匹配 ack=true，再到温度 26 的 ack=false 上报，给出最终状态。
- 任务：提出一个未来协议级改进方向及配套测试，但明确其不属于本仓库现有能力。
- 学生提交物：两条轨迹、取消能力边界声明和一段不超过 150 字的验收结论。
- 验收/评分点：同目标歧义 5 分，idle 分支 4 分，取消/本地通知边界 3 分，改进与现状区分 3 分。
- 作答边界：不能假设已有 wire 事务 ID，也不能把取消解释为撤回车辆命令。

<details><summary>参考答案与评分提示（先独立完成）</summary>

**07-01**

- `CarService::m_climate` 是最近确认/同步的状态；控件值是编辑目标；`m_pendingClimateTarget` 是受理时冻结的完整目标。
- 默认值为 22℃、风量3、模式0、AC=true、auto=false；编辑与发送均不提前覆盖已确认状态。
- UI 的 `m_pendingRequestId` 是本地请求归属凭据，0 表示无请求，不是另一份温度/风量状态，也不测量实际温度。

**07-02**

- 匹配五字段为 temperature、fanSpeed、blowMode、acOn、autoMode；解码还必须含 ack，随后 clamp 再比较状态。
- pending：匹配 ack=true 才确认，错误字段 ACK 与 ack=false 均忽略；两字节帧缺 ACK 字段，解码失败不改状态。
- idle：ack=true 忽略；ack=false 且值变化则同步并通知，重复值不重复通知。CAN 链路 ACK 不等于此应用层确认。

**07-03**

- UI 250ms 单次 debounce 从最后调节算，每次编辑重启；回填停止它并设置 `m_syncing` 防递归。
- 服务 600ms 单次 ACK timer 从受理算，确认/正确取消/stop 停止；到期只清 pending 并发超时，不提交目标。
- 有 pending 立即返回 0，不覆盖目标；编码失败也返回 0。非零 ID 递增且跳过 0，未编码进 payload。
- CAN 未打开或发送失败仍可得到非零 ID，因此只证明本地受理；不能证明传输或执行。

**07-04**

- byte0=`24=0x18`；byte1=`5+(0<<4)+(1<<6)+(0<<7)=0x45`；命令 byte2 的 ack 位为 0。
- 命令 `18 45 00 00 00 00 00 00`（前三字节 `184500`）；ACK `18 45 01 00 00 00 00 00`（前三字节 `184501`）。
- 防抖截止依次为 250、350、430ms，前两次被重启；430ms 受理一次，ACK 截止为 1030ms。
- 430ms 前控件编辑变化，已确认仍是默认值；430ms 后 pending 冻结 T。500ms 错风量与 550ms 普通上报都忽略。
- 700ms 正确 ACK：停 timer、清 pending、先提交 T，再发 `climateAckOk(id)` 和 `climateStateChanged(T)`；UI 清编号并显示“已确认”。
- 删除 700ms 回传：1030ms 超时，已确认仍为默认值；UI 回填 22℃/风量3，显示“超时未确认，已回滚”。

**07-05**

- 四场景在 900ms 的 `(ack,timeout,cancel)` 次数依次为 `(1,0,0)`、`(0,1,0)`、`(0,0,1)`、`(0,0,1)`。
- ack 场景约 100ms 提交 T；timeout 约 600ms 结束，其余约 100ms 取消；所有场景终点均无 pending，后三者仍为默认状态。
- 50ms 错误 ACK 不改变 pending/confirmed；五个单字段变体都应被拒绝，缺第三字节同样不更新。
- 重入返回 0，原目标/编号不变；0 与错误 ID 取消返回 false，正确取消后不得再发本请求 timeout。
- 断言片段（非完整测试）：`QCOMPARE(ackSpy.count(), 1);` 应放在同步正确注入之后，不用 `wait()` 等已经发生的那次信号。
- 模型必须区分“不发送真实帧”与“本地仍受理”；仅测试温度而未检查其余字段不能获完整匹配分。

**07-06**

- 0/60/120/180ms 调节只在 430ms 发送一次最终目标。回填停止未发 debounce，`m_syncing` 阻止变化信号再排新请求。
- 三个结果入口都先检查当前 ID 非零且与参数相等；0、r1 不应影响 r2 的值、编号、取消按钮与等待文案。
- 当前 r2 的正确结果各自清编号、禁用取消按钮并回填 getter；成功/超时/取消文案分别为“已确认”/“超时未确认，已回滚”/“已取消”。
- 返回 0 时 UI 不持有 pending，不锁死，取消按钮禁用，回填已确认值并显示“发送失败，已回滚”；不能取消外部请求。
- `m_pendingRequestId` 可挡住新发送；`setPanelEnabled()` 未禁用温度 +/-，因此显示仍可能变化，这是现有缺陷。

**07-07**

- `--sim` 不打开 CAN，也不产生空调 ACK；本地受理后超时是当前默认边界，应先查发送警告与 timer，而非先改超时阈值。
- UI 为 QButtonGroup：0面部/1腿部/2除霜/3上下，与 SystemState 注释一致；DBC 注释为0吹面/1面+脚/2吹脚/3除霜。
- 解析器忽略 `CM_` 注释，不会自动重排模式；数字往返不能解决文字语义冲突，需协议双方另行统一。
- 循环风没有协议字段，也没有接入命令发送；不能用“按钮可点击”证明已支持。
- +/- 未全部禁用是 UI 锁定缺口；pending 快照不会因此被覆盖，拒重入也不等于全部控件锁定。以上三处都仍未修复。

**07-08**

- r1 取消只停止本地等待，不发反向指令、不撤回已发命令；r2 目标与 T 相同，200ms 的旧 ACK 会被当作 r2 的确认。
- 原因是线上只有五字段与 ack，没有事务编号；服务发的是当前 r2 的结果。220ms 旧 r1 本地通知会被 UI 编号检查忽略。
- 不创建 r2 的分支：取消后匹配 ack=true 被忽略，随后 ack=false 的 26℃上报更新已确认状态并同步 UI。
- 可建议未来在线协议加入双方回显的事务 ID，并测试“相同目标、不同编号”的迟到回传；这需协议修改，不是已有功能。
- 合格结论把“本地串行/旧通知过滤已实现”和“同目标旧 ACK 无法辨认、硬件执行未验证”分开陈述。
