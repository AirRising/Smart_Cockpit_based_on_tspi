## 1. 为什么教程要写“还没做好”的部分

教学项目最重要的不是功能列表长，而是每一项结论能被验证。界面上有一个按钮，不代表已经发出车辆命令；测试全绿，不代表测试已经覆盖实际故障。

本页按当前源码区分已修复行为、协议限制和待完善事项。这里的待修复项是练习题，不是本轮文档更新偷偷加入的新功能。

## 2. 已有回归保护的行为

| 行为 | 当前实现与证据 |
| --- | --- |
| CAN 解析不按错误长度访问内存 | [核心实现](../src/core/CanFrameParserCore.cpp) 按真实位布局检查字节数；[核心测试](../tests/tst_core_cxx.cpp) 与 [Qt 适配测试](../tests/tst_canframeparser.cpp) 覆盖跨字节、非法布局、确切编码字节 |

| 空调取消与不同目标旧回执 | [车辆服务](../src/core/CarService.cpp) 取消匹配请求并停止计时，完整目标匹配后才确认；[服务测试](../tests/tst_climateservice.cpp) 与 [UI 测试](../tests/tst_ui.cpp) 验证旧 ID、旧目标、回滚 |

## 3. 协议和设计上的明确限制

### 空调本地请求号不在报文中

`requestId` 只用于进程内关联 UI 与服务通知。0x200 只有五个状态字段和 ACK 位，不能区分“很早以前请求的 24℃ 回执”和“这次请求的同一组 24℃ 状态回执”。

要彻底关联交易，需要协议双方增加并回传事务标识，设计序号范围、回绕、重试和去重规则。只加一个本地计数器不是协议升级。

取消只结束本地等待，不能撤回已经在总线上发出的命令，更不保证执行器恢复原状态；最终实际状态需要车辆反馈。

### 摄像头恢复不是自动重连

错误后服务停止，可以再次调用 `start()`。当前没有自动退避重试、设备重枚举或重连按钮；不要把“可重启”写成“会自动恢复”。轨迹线也只是随转角变化的示意，未做相机/车身几何标定，不能用于实际碰撞距离判断。

### DBC 不是完整标准实现

解析器支持本项目需要的 BO_/SG_ 子集，未知内容可能被忽略，加载失败可能已修改部分定义。数值用 double 表示，不保证全部 64 位整数精确表达；范围字段不代表所有输入自动获得验证。业务层要求固定信号名，也不会适配任意车型协议。

## 4. 当前仍需完善的问题与对应练习

| 问题 | 当前后果 | 建议先写的测试，再考虑实现 |
| --- | --- | --- |
| [ScreenManager](../src/ui/ScreenManager.cpp) 同优先级返回没有最近访问次序 | 退出倒车可能回到非刚才的普通页 | 枚举普通页访问排列，挂 R 再退出，检查返回页面；不要依赖 QHash 遍历顺序 |
| [ClimatePage](../src/ui/ClimatePage.cpp) 循环风按钮没有协议链路 | 按钮样式改变不代表发送车辆命令 | 定义按钮的期望与协议字段；协议没定义前禁用或标明演示，而不是假确认 |
| 空调等待时温度 ± 未完全禁用 | 显示可被改变，但并不会自动产生新请求 | 等待 ACK 时逐个操作输入入口，检查目标和显示是否一致 |
| [CanManager](../src/core/CanManager.cpp) 发送扩展帧仍使用标准 ID 掩码 | 29 位 ID 被截断 | 用测试替身捕获 can_id，断言扩展 ID 和标志位；不要发到真实车辆验证 |
| [MediaService](../src/media/MediaService.cpp) 播放状态下直接换 URI | 界面换曲名，实际音频可能仍是旧曲 | 播放 A 后切 B，核对实际 URI/输出，而非只检查标签 |
| 媒体总线无消息时提前返回 | 进度查询不稳定，进度条可能不动 | 在没有新 bus 消息时推进时间，确认位置查询仍发生 |

附加排查题：相同长度两首歌的时长缓存、进度拖动与位置刷新竞争，也应作为媒体章节的后续回归用例。

摄像头像素格式也尚需修正：当前将 `0xFFRRGGBB` 整数写入 `Format_RGBA8888`，在小端机器上红蓝互换。黑白测试球与现有启停用例无法证明颜色正确；按 [09](09-camera-and-reverse.md) 增加彩色像素的独立已知答案测试，再统一写入与图像格式。

### 配置与文案还需要统一

- [SystemState.h](../src/core/SystemState.h) 的 `blowMode` 注释与当前页面编号一致，但与 [DBC 注释](../config/vehicle.dbc) 存在差异。应让协议双方确认整数含义，再同步代码、DBC、文档和测试；本轮没有擅自更改协议。
- [原交叉工具链](../cmake/toolchain-aarch64-linux-gnu.cmake) 的编译器前缀拼接缺连字符，不能承诺原样 Cross 构建成功。
- [原部署脚本](../deployment/deploy.sh) 的默认构建路径与预设不一致，首次部署缺配置目录，且会立即操作远端服务。按 [12](12-cross-build-and-deployment.md) 分阶段操作，不盲目执行。
- [默认服务](../deployment/smart-cockpit.service) 以 root 运行、没有传真实摄像头参数；显示配置也依赖特定设备。它是待适配模板，不是通用安装器。

## 5. 五道综合题

### 题一：增加冷却液温度

自己设计一个**仅用于本地教学**的新信号，先确定 ID、位段、系数、范围和单位，再补核心表、外部 DBC、服务状态/信号、模拟器、页面与测试。避免与既有位段重叠。

验收：手算字节与解码一致；字段缺失不污染旧状态；异常值有明确处理；没有在 UI 中重新解码 CAN。

### 题二：把空调状态机画出来

画出空闲、等待、确认、超时、取消和请求被拒绝的转换。标出哪些事件改变 confirmed state，哪些仅改变 pending state。

验收：能解释收到不匹配目标 ACK 时为什么继续等待；为什么取消后 ack=true 与 ack=false 不能混为一谈；为什么无 CAN 时非零 ID 不证明命令已传输。

### 题三：设计摄像头自动重连，而不是只加 while

先不写代码，列出重试间隔、上限、退出取消、设备变化、generation 和状态提示。禁止阻塞 GUI 线程等待设备恢复。

验收：故障期间不显示旧画面；退出能终止重试；恢复后旧会话帧不能进入新会话；记录重连尚需硬件验证的部分。

### 题四：评估日志系统的承诺

解释 `flush()` 与 `fsync()`、无界队列与有界队列、正常 stop 与突然断电之间的区别。设计日志队列积压和退出时写入的测试，不以“有一个日志文件”作为可靠性证明。

验收：能说清当前实现没有保证哪些事，并说明需要更多可靠性时的成本。

### 题五：修复一个已知问题并证明没有回归

从第 4 节选一个独立问题：先给出最小复现，再写会失败的断言，修改实现，重跑相关测试，最后验证真实交互。

验收：不能通过删测试、放宽期望或只改 UI 标签让测试变绿。修改协议或部署权限应单独评估，不能作为附带清理。

## 6. 毕业验收矩阵

| 层次 | 必做 | 不能替代什么 |
| --- | --- | --- |
| 语法与构建 | 从独立目录构建自己的窗口和分层实验 | 不等于完成车辆系统 |
| 算法 | 确切字节、边界、非法布局、短帧、输出不污染 | 不等于接上真实 CAN |
| 服务 | 空调成功/超时/取消/旧回执，相机停止/错误/重启 | 不等于真实 UI 正确显示 |
| 桌面交互 | 导航、仪表、空调、实际视频帧、媒体真实播放 | 不等于板端驱动和权限正确 |
| 板端 | 架构/库、显示、音频、摄像头、隔离台架 CAN | 不等于整车安全认证 |

若只完成前几层，就准确写“完成到哪一层、缺什么条件”。板卡、真实 CAN、实体相机和音频设备没有实际验证时，不能写“全平台验证通过”。

结束时应能用自己的代码演示：**一帧数据进入仪表、一条命令获得确认、一次设备失败被清晰呈现**。这比背诵所有类名更接近真正学会。
